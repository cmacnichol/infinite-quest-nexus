# Campaign cast operations

## Discovery rollout status

Automatic discovery has passed the phase-04 legacy-surface acceptance audit. `CAST_DISCOVERY_ENABLED` defaults to `false` and takes effect only while `CAST_EDITING_ENABLED` is also `true`. The worker and combined runtime roles process durable discovery jobs through a capacity-one optional lane when enabled. The API-only role does not run that lane. Accepted append and replacement commits enqueue discovery atomically using preparation saved outside the commit transaction. If preparation is unavailable, the story still commits with a failed discovery job labeled `admission_unavailable`. Lifecycle, coverage, retry controls, and physical-attempt limits are implemented. See the [acceptance evidence](../review/campaign-cast/phase-04-acceptance.md). Deployment remains an explicit operator action.

When discovery is enabled, API and worker text calls share PostgreSQL capacity leases. Apply migration `0109_text_provider_capacity` first. Set `TEXT_PROVIDER_CONCURRENCY` consistently on every API/worker replica (default `2`, range `1`–`1000`) and enable discovery consistently across those replicas; a replica with discovery disabled does not participate in this guard. The limit covers text/intent generation, including text preparation for illustrations, but not image or embedding requests. Waiting consumes the request deadline and does not reserve or dispatch a prepared physical attempt. Sequential fallback candidates retain the same capacity slot. Provider work holds no database connection for this guard.

Leases expire after the request deadline plus five seconds to recover capacity after process loss. Cancellation propagates to the transport and normal release waits for provider work to settle. This bounds live local leases; it cannot prove that a remote provider stopped processing after an aborted connection or crashed process. Rollback disables discovery and retains this operational table until all participating processes have stopped; leases are excluded from portable archives and carry no story content or credentials.

New discovery plans use the saved text-provider route and its exact qualified nonstream schema, a 120-second request deadline, and at most 4,096 output tokens (smaller provider/model limits still apply). The discovery job lease includes another 60 seconds for checkpoint and publication work. Existing frozen 30-second plans remain valid. Capacity deadline expiry is reported as `provider_timeout`, rather than caller cancellation. Physical calls are recorded under operation `cast_discovery`, attributed to the source campaign and turn. Checkpointed responses survive worker interruption and are reused for publication. Disabling discovery prevents new claims and publication without disabling manual editing; it retains jobs and evidence for recovery. No relationship inference is enabled by this gate.

To recover an exhausted scan created under the old limits after deploying this fix, cancel it, preview the same range, and start a new scan. The new scan adopts cancelled jobs without saved output using its newly frozen settings. Completed work and paid checkpoints remain intact. Attempt counts are retained: an exhausted turn will still require **Retry** in the new scan's controls before another paid request is allowed. Retrying the original scan alone keeps its original frozen settings. No production scan is automatically restarted by deployment.

Phases 02–03 provide manual supporting-character APIs, history/backup integration, and the legacy Story cast editor. Generation context and optional history backfill have separate gates. The Characters revamp adds a shared workspace in both Story clients; see the [revamp verification record](../review/campaign-cast/revamp-acceptance.md) for current checks. See the [implementation specification](../superpowers/plans/2026-09-22-campaign-cast.md).

## Generation context gate

`CAST_CONTEXT_ENABLED` defaults to `false` in runtime configuration, Compose and Swarm. It takes effect only when `CAST_EDITING_ENABLED` and `CAST_DISCOVERY_ENABLED` are also true. Configure all replicas consistently. The capability applies to newly queued jobs for campaigns enrolled in Story Memory; Story Memory Off retains its compatible generation path. The [phase-05 acceptance audit](../review/campaign-cast/phase-05-acceptance.md) records deterministic Action/Story Direction proof and the shared test-bootstrap limitation; this flag has not been enabled in a deployment.

Enabled jobs freeze cast authority with `generation-base-v4`, `story-v17-campaign-cast` and `current-continuity-v4`. Both Action and Story Direction include selected, source-linked cast records within existing context ceilings. User field corrections take precedence from their effective turn. Incomplete tracking is disclosed in private context, with stale dynamic fields omitted rather than asserted as current. Existing history remains available as dated evidence. The initial cast allocation is at most 3,000 tokens and 10% of available context; it does not increase campaign or provider budgets.

To roll back context injection for new jobs, set `CAST_CONTEXT_ENABLED=false` and restart/redeploy through the normal deployment procedure. Keep the compatible application version for in-flight jobs: their frozen cast capability and authority remain in force. Stored identities, evidence and edits are retained. Disabling discovery also prevents new jobs from enabling cast context, without clearing existing cast data. No relationship inference or automatic historical backfill is enabled by this flag.

## History scan rollout status

Phase 06 has passed its legacy-surface acceptance audit. `CAST_BACKFILL_ENABLED` defaults to `false` in runtime configuration, Compose and Swarm and requires editing plus discovery. The worker schedules explicitly persisted scans through the existing discovery lane; enabling the flag does not create scans or enumerate historical campaigns. Configure API and worker replicas consistently. See the [phase-06 acceptance record](../review/campaign-cast/phase-06-acceptance.md).

Disabling this flag stops scan scheduling, claims, retries and publication while retaining saved checkpoints and applied cast authority. Forward discovery remains available when its separate gate is on. Expired scan leases release the campaign running slot when forward work needs it. Keep additive scan migrations 0110–0111 and their provenance; their down migrations reject removal while retained operational records exist. No deployment has enabled this capability.

Scan endpoints are under `/api/v1/campaigns/:campaignId/cast/scans`: POST `/preview` validates the range and estimates remaining chunk requests; POST the collection explicitly starts a scan; GET the collection returns the latest scan and `capabilities.castBackfill`; GET `/:scanId` returns progress. POST `/:scanId/pause`, `/resume`, or `/cancel` with an empty object controls it. Preview/Start require `fromTurn`, `throughTurn`, `expectedBoundary`, and `idempotencyKey`; the server resolves ownership and text-provider selection. Requests reject additional fields. Repeated identical Start keys retain the original scan without repeating provider preparation. Failed preparation leaves no scan, and a changed boundary returns conflict after preparation. Read and cancel remain available when editing/backfill are disabled. Cancellation keeps already applied characters and evidence. Estimates exclude possible retries and do not promise exact cost.

For an explicit failed-turn retry, POST `/cast/scans/:scanId/retry` with `turnNumber`, `expectedCastRevision`, `expectedBoundary`, and `idempotencyKey`. Progress supplies `firstFailedTurn` for the next failure. Retry reuses discovery retry generations and preserves completed chunks, parsed checkpoints, and prior physical accounting. Repeating the same key for that scan turn grants no additional allowance. A paused scan stays paused; a cancelled scan cannot retry. A retry authorized through a scan becomes scan-controlled work, including a reused forward failure. If the reused forward job lacked admission, retry uses the execution plan frozen at scan Start. No fresh provider metadata lookup occurs inside the retry transaction. An oversized source without a dispatchable job cannot be repaired by spending another provider attempt. If a scan stops at a turn that already exhausted forward discovery, use **Retry turn** inside the existing scan to continue the range. The initial scan can show a failure before making a new provider request. If the player instead retries the original job through character tracking, publishing its final chunk also clears that turn’s scan failure. A paused scan stays paused.

Pause is checked again at physical reservation and dispatch. Responses already dispatched may finish accounting and checkpointing. A pause before any dispatch requeues the job without spending an attempt; already dispatched calls retain their accounting and exhausted allowances remain failed. Resume retains the original execution plan and checkpoints.

## Enable and disable editing

`CAST_EDITING_ENABLED` defaults to `false` in runtime configuration, Compose, and Swarm. After applying migrations through `0103_campaign_cast_lifecycle`, an operator can set it to `true` and restart/redeploy the API through the existing [deployment procedure](deployment.md). `/api/v1/meta` exposes `capabilities.castEditing`; cast read responses also include this capability. No deployment was performed as part of implementation.

Set the flag to `false` to stop new cast mutations. Reads and Campaign/System Archive preservation remain available. Keep stored authority and the additive schema in place; do not narrow historical-provenance constraints or delete tables as a feature rollback. The SQL down section only removes the operational boundary key and intentionally retains the widened provenance constraints. Older application versions without cast-aware archive support must not be used to export these campaigns.

## API contract

The server resolves the owner. Routes under `/api/v1/campaigns/:campaignId/cast` provide GET list, POST create, GET `/:characterId`, and PATCH `/:characterId`. Lists accept `query`, a UUID `cursor`, and `limit` from 1 to 50. Request bodies are limited to 64 KiB.

Writes require `expectedCastRevision`, `expectedBoundary` (turn number and timeline revision), and an `idempotencyKey`; edits also require `expectedCharacterRevision`. Read the current response before writing. Reusing an identical request returns its original receipt, even after another edit; reusing its key with different contents returns a conflict. On a stale-revision conflict, reread and reconcile rather than blindly resubmitting an old edit.

Create accepts a name, aliases, and a sparse profile. Edit supports name/aliases, `setOverrides`, `clearOverrides`, `pinned`, and `ignored`. Setting a field to an empty string deliberately overrides any discovered value; clearing that override restores the supported discovered value, or leaves the field unknown when none exists. Names are not identity keys, so two characters can share a name. There is no public delete operation.

Detail returns observations, current overrides, identity-event evidence, automatic attachments, and `unresolvedCandidateIds`. Protagonist writes return `cast_protagonist_read_only` and the existing `editorDestination`; its profile authority stays in the existing protagonist system. Pin/ignore flags influence selection when the separate character-context gate is enabled.

| Response | Meaning |
| --- | --- |
| 404 `cast_not_found` | Missing or foreign resource |
| 409 `cast_revision_conflict` | Stale cast, character, or timeline boundary |
| 409 `cast_generation_active` | Queued, active, or recoverable generation prevents an authority edit |
| 409 `cast_idempotency_conflict` | Same key used with different input |
| 422 `cast_invalid_request` | Invalid contract or fiction value |
| 422 `cast_protagonist_read_only` | Use the existing protagonist editor |
| 503 `cast_editing_disabled` | Operator gate is off |

## History and portability

Explicit identity review ignores aliases that repeat the proposed name. Attaching to a selected existing character can resolve pronoun-based identity evidence without a literal name in the quotation. This identity-only decision preserves the target's name and aliases; source integrity, ownership, current-history, instruction, and hypothetical-identity checks still apply. Attribute observations are validated separately under the existing stricter rules, and unsupported details remain pending. Automatic discovery and new-character creation still require name evidence.

`GET /api/v1/campaigns/:campaignId/cast/discovery` reports the independent discovery capability, forward enrollment start, contiguous tracked-through watermark, first gap, and unresolved identity count. The first eligible accepted source records enrollment; earlier history is not implicitly tracked. Missing or failed source revisions stop the watermark even when later sources completed. Correcting a completed source withdraws its coverage until the replacement finishes; rewinding before enrollment clears it. Unresolved identity candidates do not themselves make successfully processed narration incomplete.

Migration `0107_campaign_cast_coverage` adds the enrollment start and backfills existing active discovery jobs. Enrollment and jobs are operational state excluded from archives; restored/branched/transferred authority does not imply historical discovery coverage. Branches and world transfers inherit an enrolled source's forward enrollment starting after the copied history. They do not copy jobs, leases, failures, or pending proposals, and do not initiate a history scan. Unenrolled sources remain unenrolled until their first eligible accepted turn. Rollback can disable discovery while retaining editing and recorded evidence. The migration's down direction drops only the enrollment column.

The legacy Characters panel displays this status and provides **Refresh characters**. Tracking-status failures leave saved characters accessible. **Review character matches** shows pending source quotes, a source-turn link, existing-character search and profile preview, and explicit attach/create actions. Eligible failed jobs expose **Retry character tracking**. A conflict requires refresh; provider recovery errors leave the same retry request available. Shared provider concurrency remains pending, so do not enable automatic discovery as a released feature yet. The old placeholder tracking fields were removed from the cast snapshot/list contract; consumers must read the dedicated status endpoint. No web-next UI was changed in this slice.

`GET /cast/candidates` accepts an optional UUID cursor and a limit of 1–50 (default 20). `POST /cast/candidates/:candidateId/resolve` accepts the standard expected cast revision, boundary, and idempotency key plus either `{ action: "attach", characterId }` or `{ action: "create" }`. It uses the editing capability. Source correction, a stale boundary, or active generation prevents a new application; matching receipt replay returns the original result while its source remains current. Unsupported identity evidence still fails validation. A valid identity can be saved even when some or all proposed attributes fail validation: only supported observations are applied, and `pendingObservations` records the original indexes and reasons for withheld details. The original proposal stays intact and pending. Applied identity decisions are recorded as source-backed mentions, preserving last-seen history and archive recovery without inventing profile facts or overwriting the main-character profile.

After partial resolution, the unfiltered candidate list includes `resolvedCharacterId` and projects only the withheld observations. The Character matches screen requests `view=matches`, which excludes identities already attached or created and candidates explicitly linked to ignored cast identities before pagination. It does not hide unresolved people merely because they share a name. The default `view=all` retains access to pending evidence, and ignoring a character does not delete it; removing Ignore makes unresolved matches for that identity visible again. Pending-evidence counts may still include withheld details for a saved identity. Manual edits can record confirmed details; they do not silently approve or clear the pending evidence. The Characters detail inbox now provides explicit confirmation and dismissal; confirmation stores a user correction, while dismissal changes only the operational inbox. Existing pending candidates need no migration or new scan: after deploying the updated API and browser assets, reload matches and repeat the identity decision.

Rewind/undo removes cast edits and identities beyond the retained history boundary. Retained source-supported observations and explicit edits remain; discarded future edits cannot return when a new timeline reaches the same turn number. Branching remaps retained character, event, observation, and turn IDs into the destination campaign. Claims retain their speaker identities even when those identities are currently hidden.

Narration correction and accepted-turn replacement invalidate facts whose effective source revision/hash no longer matches. User overrides remain authoritative. Each boundary change advances a timeline revision so stale internal batches cannot recreate discarded state. The same transaction reconciles already-enrolled discovery sources: discarded or changed sources lose their jobs and pending candidates; changed retained narration is queued with its frozen admission. Unchanged retained sources advance to the new timeline while preserving published chunks, parsed checkpoints, retry counts, and failure status. Active leases are revoked. No new source is enrolled by this reconciliation, and disabled workers remain disabled.

Cross-world transfer retains historical origins and effective narration corrections. Campaign imports remap IDs and bind ownership to the server-resolved destination owner. If the source world is absent from a Campaign Archive, `historical_world` stores provenance without claiming that the source entity belongs to the destination world.

Campaign Archives and System Archives embed version 1 cast authority: identities and retained events/evidence, including blanks, flags, and overrides. They omit projection caches, operational receipts, provider payloads, and leases. Import validates bounds, chronology, and references before writing, then rebuilds projections. Old archives without cast remain valid; unknown newer cast versions fail explicitly. Archive preservation does not depend on the editing gate.

## Verification and recovery

The legacy Characters panel exposes **Scan earlier story** when backfill is enabled or a prior scan exists. Preview a continuous accepted-turn range before Start; the preview reports the selected model, estimated requests and already completed turns. Estimates exclude retries and are not price quotes. Use Refresh scan to update progress, Pause/Resume to control new dispatch, and Cancel to stop remaining work while retaining applied characters. Retry failed turns through the scan controls so progress and physical-call accounting remain atomic. Earlier history outside the selected range remains untracked. Pending character matches require separate review. Scan controls are currently legacy-only; web-next is deferred.

Discovery recognizes both playable characters and character/person/NPC entities from the campaign's pinned world version. It sends source-relevant identities plus the protagonist, capped at 24 entries and 2,000 estimated identity tokens; the complete captured roster remains available for identity validation. Hints contain short complete fiction values only. Ambiguous names or conflicting world IDs require explicit review instead of automatic merging. This selection affects extraction only; generation-context integration remains phase 05.

Automatic discovery allows two physical provider dispatches per job/source chunk across fallback routes and worker reclaims. Unknown dispatched outcomes consume the allowance; unsent reservations and checkpoint publication do not. Later chunks receive their own allowance. Migration `0108_campaign_cast_discovery_retry` supplies explicit retry generations and idempotent receipts, preserving prior accounting while granting a fresh two-call allowance. It also preserves completed chunks and saved output. Use `POST /cast/discovery/:jobId/retry` with `expectedCastRevision`, `expectedBoundary`, and `idempotencyKey`, or the legacy Retry button. Repeating the same request returns its original generation. Existing frozen admission is retained; admission-unavailable jobs prepare the selected/default text provider outside the write transaction and revalidate before queuing. Recovery failures return 503 without modifying the failed job. Do not reset attempts or generations directly in the database. Down migration rejects nonzero retry generations; disable discovery for operational rollback. Retry receipts are operational and excluded from archives. Shared provider concurrency is described in the rollout section above. An exhausted allowance currently surfaces through the generic discovery provider-failure diagnostic.

See the [revamp verification record](../review/campaign-cast/revamp-acceptance.md) for current evidence and verification limits; the [phase 02 handoff](../review/campaign-cast/phase-02.md) records the earlier release. Cast projections are rebuilt from retained authority and revalidate source narration on reads. Accepted turns and user edits remain the recovery sources; do not repair a disagreement by rewriting the cached profile directly.


## Characters revamp and automatic matching

Apply additive migrations `0117_cast_attachment_metadata`, `0118_cast_detach_review`, `0119_cast_detail_decisions`, and `0120_cast_workspace_revision` before using the revised clients. `CAST_AUTO_MATCH_ENABLED` defaults to false and requires editing and discovery. Configure it consistently in the combined role or both Swarm services. New admissions use strict matching with `cast-discovery-prompt-v1` unless the effective auto-match gate is enabled; eligible new admissions then freeze `unique_name` and `cast-discovery-prompt-v2`. The output protocol remains `cast-discovery-v1`.

Turning off only auto-match stops new relaxed admissions. Already admitted jobs retain their policy and can drain. Turning off discovery stops claims/publication under the existing gate. Editing, source history, and **Not this character** remain available when editing is enabled. Ambiguous names, competing aliases, and uncertain details still require review. An automatic identity association does not establish physical presence.

Undo appends a detach event; it does not erase a character or rewrite accepted turns. Durable attachment metadata carries the source ranges and affected observations. The inbox reconstructs an identity-only review item from retained valid narration when the original extraction candidate has expired or was omitted from an archive. This requires no provider request. Source correction invalidates evidence, and rewind replays only decisions retained at that boundary.

The combined review inbox requests `view=review` and distinguishes dated observations from user corrections. An `accept` detail decision takes the unchanged, eligible value from the stored proposal, checks the retained narration, and records a fact with its source turn, revision, paragraph, quote and hash. The receipt links the resulting observation; retrying the same request cannot append it twice. Existing `confirm` requests retain override semantics, including intentionally blank values. Existing overrides are not reinterpreted. Dismissing adds no fact. Earlier clients can continue requesting `matches` and `details` without receiving the new eligibility field.

For installations that want fewer manual matches, explicitly set `CAST_AUTO_MATCH_ENABLED=true` on the combined runtime or consistently on API and worker replicas, with editing and discovery enabled. This applies to newly admitted work. It does not clear old inbox items or change frozen scans; remaining ambiguous identities still need review. No deployment change or historical scan is implied by installing the review interface.

Dismissals suppress matching observation content from the same turn and narration revision across retained review proposals, including a repeat scan. A changed observation or narration can be reviewed again. Workspace diagnostics report retained identity decisions and confirmed or dismissed fields as aggregate counts capped at 10,000; they include no names or quotations.

While `CAST_AUTO_MATCH_ENABLED` is effective (it requires discovery and editing), character text references are recorded without a provider call after accepted narration and narration corrections. With auto-match off, no lexical mention work runs. **Last mentioned** is textual recency; **last observed** remains established evidence. Neither alone claims current location or presence. Optional mention failures roll back to a savepoint and do not reject an accepted story.

Cast archives now export version 2. Readers accept legacy version 1 and reject unknown newer versions. Branch, transfer and import remap attachment events, source ranges and observation IDs. Operational discovery jobs, inbox dismissals and receipt queues are not portable; confirmed overrides and undo authority are portable. Imported history creates no paid scan automatically. New discovery or an explicit scan may present previously dismissed evidence again.

Back up before rollout and deploy compatible readers before enabling new writers. A v1-only binary is not a safe rollback target after v2 authority exists. Keep additive migrations and use the v2-aware binary with gates disabled for rollback. Production enablement, a copied-campaign canary, historical scanning, and live provider verification remain separate operator work; this implementation does not perform them.


Workspace status uses a scoped revision token to reuse unchanged projections. Candidate/job/authority changes invalidate the cache through database triggers; unchanged polling does not hash narration or project the full roster. The token is operational and not exported.

**Context preview** is an explicit estimate from the shared generation planner over current campaign authority, prompt overrides, and Story Memory policy. It does not call a model or initiate retrieval/discovery. Character context is reserved before optional Chronicle candidates, so preview does not need an embedding request. Continuity review uses the same request-budget estimator and separate reviewer cap. When compatible settings are saved locally from a prior admission for the same unchanged provider profile and selection, preset and reviewer requests use the shared frozen serializer. A preset or custom reviewer without compatible saved settings reports unavailable. Direct models without saved routing use configured limits. Final provider routing, verified output format, action assessment and later state changes can alter selection; the UI discloses this estimate. Story Memory Off and disabled character context report their reasons. The preview is not a historical audit of a completed turn.
