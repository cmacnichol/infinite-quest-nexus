## Finding and deviation from the original T16 file plan

The original T16 plan names Story DOM/CSS plus one browser test and assumes explicit older/newer groups can be loaded from current pages. That client-only list cannot provide bounded traversal from a saved far-old Turn 12: the exact reader lookup returns one full turn but no cursor or history version; /campaigns/:id/turns accepts only a server-issued older cursor from a recent page; reader search returns excerpts, not scenes. Gapped accepted turn numbers are permitted by imports/transfers and the database uniqueness constraint. Arithmetic exact requests for n±1 are not valid adjacency and repeated exact requests would be separate snapshots. A cursor walk from the latest page to an old pin is not bounded. This proposed additive reader-history seam is therefore an explicit cross-layer deviation and prerequisite, not a claim that existing T16 client-only interfaces already work.

Existing source evidence: packages/contracts/src/reader-history.ts defines {campaignId,turn} for exact lookup; packages/client-web/src/reader-history-api.ts exposes getTurn/searchHistory only; packages/database/src/reader-history-repository.ts reads exact turns separately and search summaries under a snapshot; packages/database/src/play-loop-read-repository.ts accepts only an opaque backward cursor. The public full-scene projection is turnSummarySchema in packages/contracts/src/client-api.ts. Database migration 0001_initial_nexus.sql supplies UNIQUE(campaign_id,turn_number) and turns_owner_campaign_idx(owner_user_id,campaign_id,turn_number), not gap-free numbering. Migration 0070_turn_narration_corrections.sql supplies the effective_turn_narrations view and correction lookup index.

## Proposed smallest additive public seam

Add GET /api/v1/campaigns/:campaignId/reader/scene-window through the existing reader-history route registration, application use case, repository port, and typed client adapter. Do not alter /turns, sync-status, SSE, exact getTurn, reader/history search, or their cursor shapes. Proposed query and response (field names to freeze before coding):

```ts
type ReaderSceneWindowRequest = {
  anchorTurnNumber: number; // positive integer
  anchorTurnId: string; // UUID, exact accepted identity
  direction: 'older' | 'newer';
  neighborLimit?: number; // integer 1..9, default 9
  historyToken?: string; // opaque campaign-bound token returned by a prior scene-window read
};
type ReaderSceneWindowResponse = {
  campaignId: string;
  anchor: { turnNumber: number; id: string };
  direction: 'older' | 'newer';
  turns: TurnSummary[]; // 1..10, ascending accepted turnNumber; anchor last for older, first for newer
  hasMore: boolean; // further actual neighbors in requested direction
  historyToken: string;
};
```

The server includes the authoritative anchor as one of the at-most-10 turns, plus at most nine actual neighboring accepted turns. An empty neighbor set returns just the anchor with hasMore=false. The response schema should reject duplicate turn IDs/numbers, out-of-order rows, wrong anchor edge/identity, and >10 scenes; the client adapter validates the same schema. This route returns only the already-public effective TurnSummary projection. It must never include private mechanics, state snapshots, scratchpads, raw model output, rejected narration, imported provenance, or an owner ID.

The historyToken is an opaque base64url envelope with exactly schemaVersion=1, campaignId, and sceneFingerprint (64 lowercase hex SHA-256), with a maximum encoded length of 4096. It is a consistency token, not an authorization grant, held PostgreSQL snapshot, or arbitrary seek cursor. The client passes it on a subsequent scene-window request in the same campaign. A token from another owned campaign is invalid (400); an out-of-date same-campaign token is a safe 409 with a stable reader_history_changed code. Do not synthesize or reuse a /turns or search cursor. The first request from an exact T11 pin has no token; it receives one together with an authoritative anchor and neighbors. If the same UUID's effective narration changed since that exact lookup, install the response's authoritative anchor and neighbors atomically after client epoch checks rather than mixing the old exact row with new rows.

Error behavior should preserve existence privacy: malformed parameter/token -> 400 generic response; missing anchor ordinal or inaccessible campaign -> same 404 response; existing scoped ordinal with a different anchor UUID -> 409 reader_anchor_changed; stale historyToken -> 409 reader_history_changed. Check owner/campaign scope for the anchor before distinguishing a replacement, so cross-owner requests do not disclose a turn or campaign. A failed/stale request must leave the old client window, scroll anchor, selection, and draft intact with a retry affordance. Client campaign/load/accepted-turn/window epochs still fence late HTTP results; the historyToken protects consistency across successful requests, not user authorization.

## Snapshot, query, and index mechanism

Implement the read in packages/database/src/reader-history-repository.ts using one BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY transaction. Under the same scoped client: look up the anchor by owner_user_id, campaign_id, and turn_number, then compare its UUID to anchorTurnId, compute the new scoped sceneFingerprint, validate optional historyToken, select neighbors from effective_turn_narrations joined to turns on owner/campaign/turn ID, ordered by (turn_number,id) in the requested direction with LIMIT neighborLimit+1, then normalize narration and public audit fields. Use the existing effective narration view so corrections are reflected without exposing private columns. Return ascending rows regardless of query direction and derive hasMore from the extra neighbor; no offset paging or per-ordinal exact GET loop.

TurnSummary includes reportedCost, which the Story scene UI can display. Existing exact getTurn and /turns obtain costs through a separate provider call, so copying that pattern would invalidate a claim that every returned field came from one snapshot. For this new method, obtain costs for the at-most-10 IDs with createProviderCostRepository(client).getTurnCosts inside the same read transaction, then validate each full row with turnSummarySchema. Keep the existing exact-get behavior untouched. If this cannot be done under the same client, narrow the new response projection explicitly and do not claim full-scene snapshot consistency.

Do not reuse the existing /turns or search cursor version aggregate (turn count, maximum ordinal, latest ID, correction count/maximum revision) as this scene-window token: an interior same-number ID replacement can retain those aggregate values. Instead compute a scene-only scoped fingerprint inside the same read transaction. Query accepted turns ordered by (turn_number,id), projecting only turn_number, turn ID, latest correction ID and latest correction revision for each row; the latest correction can use the existing owner/campaign/turn/revision-desc index. SHA-256 a canonical serialization of those ordered tuples with an explicit scene-window-v1 domain prefix. This changes for append, rewind/deletion, interior identity replacement, and every append-only narration correction, even if the correction count and maximum revision would collide. Include gaps as recorded ordinals. A direct in-place mutation of authoritative turn or correction content is outside supported append-only paths and is not promised by this fingerprint. Keep current /turns and search cursor formats and version algorithms untouched. The fingerprint is O(number of accepted turns), not O(1); EXPLAIN (ANALYZE, BUFFERS) the ordered fingerprint scan, bounded neighbor query, and same-client cost query on sparse and 2,000-turn campaigns and report actual timing/rows. The existing turns_owner_campaign_idx supports owner/campaign and both directions of turn_number order; turn_narration_corrections_effective_idx supports correction lookup. Propose a new index or monotonic revision migration only if measured evidence requires it; no migration is justified by this read-only audit.

## Reader policy consequence

Keep the continuous presentation window at <=10 scenes, separate from T13's 50-card History dialog and <=100 raw History cache. Use the appropriate currently visible edge turn as the request anchor: oldest scene for Load older, newest for Load newer. Place stable group controls at their respective scene edges, so activating one brings that edge scene into the reader viewport and permits retaining its exact (turnNumber,id) and viewport offset while moving to a group with new neighbors. An arbitrary middle or opposite-edge visual anchor cannot always both remain in a contiguous 10-scene window and make progress; the provisional T16 policy's 'nearest sticky reader line' language must be constrained accordingly. On success, preserve the edge anchor node/offset and focus where possible, install the complete validated group once, and keep draft/selected-turn identity separate from scroll anchor. On error, leave the old group intact. A single far pin remains one exact scene until an explicit group action.
