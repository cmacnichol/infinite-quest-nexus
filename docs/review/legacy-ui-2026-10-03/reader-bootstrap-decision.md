# Reader bootstrap decision

Disposition: defer T28. Sol independently accepted the evidence-gate decision on 2026-10-04. No bootstrap route, contract, implementation or bootstrap regression scaffold has been added.

The post-T27 diagnostic profile ran against commit `4be68f9461ae10730e084eab9e97cd9913cefadd`, with the accepted T27 client changes at `8b52e79e`. The checkout was dirty because adjacent test preparation was present. All recorded application/core/contracts, benchmark and fixture source hashes matched before and after the run. Both implementation agents paused checks and application writes, and the owned development-server ports were free before and after execution.

The existing deterministic browser benchmark executed one warmup and three samples with 317 accepted turns, three worlds and two campaigns, using a 1280x800 Chromium viewport and mocked API routes. Its numeric exit was zero. The full report and stderr are retained under ignored `.superpowers/sdd/legacy-ui-2026-10-03/evidence/T28-post-client-profile.*`; graph snapshots are adjacent. This is a Windows/Vite diagnostic profile, not the matched Linux resource-constrained C0 release benchmark. Its timings do not establish production latency, database cost or a statistically comparable improvement.

Every sample completed the dashboard, Story, explicit history paging and warm reload journey with 20 API requests and 190,516 API response bytes. Those are whole-journey totals, not startup totals. The first Story sync response was 30,465 bytes and its required runtime-state response was 388 bytes. Six explicit history page responses ranged from 9,783 to 28,839 bytes. The corresponding reload repeated sync and state. All samples recorded zero writes, no external requests and no runtime errors; the history delay was held and explicitly released. Story DOM count was 569 and history DOM count 1,619 for this fixture.

These observations do not demonstrate a remaining reader bootstrap bottleneck. T27's executed browser cases separately show that an indefinitely delayed optional image configuration no longer prevents accepted narration and navigation, while a pending generation retains its lock. The current reader/history implementation already bounds presentation and explicit paging. The profile does not measure first-readable-scene latency or production-sized private runtime state. Large real state could still make a future public reader projection useful; that hypothesis remains unverified.

An additive bootstrap would introduce a second snapshot/projection and an additional read while sync/runtime hydration must remain for generation readiness, recovery and current-state editing. Its possible earlier-reading benefit has not been demonstrated by this profile. Introducing it now would add snapshot, isolation, stale-result and old-server fallback obligations without evidence of a material benefit. Preserve the existing contracts and complete the measured client, build and accessibility improvements instead.

Reopen T28 only after a frozen real-runtime profile attributes meaningful first-readable latency or payload cost to sync/runtime reads after client optimization. Before implementation, separately audit exact public allowlists, same-snapshot latest-turn/count, owner scoping, generation locks, accepted-result fences and 404 capability fallback. The final T35 performance record must retain this decision and its limits; a real-runtime regression attributable to these reads requires reassessment rather than treating this diagnostic profile as a pass.
