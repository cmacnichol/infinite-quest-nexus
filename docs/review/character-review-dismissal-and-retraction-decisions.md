# Character review implementation decisions

This record preserves the implementation rulings in chronological order. The [acceptance record](character-review-dismissal-and-retraction-acceptance.md) contains verification results, the final review outcome, and platform limits. These decisions describe the local implementation; they do not imply deployment or activation.

1. **Checkout and branch.** Use the existing checkout on a new topic branch to retain the installed browser and database harness while leaving the prior committed branch intact. The tradeoff was that work did not have a separate concurrent working directory.
2. **Contracts before repository.** Task 1 covered contracts, domain, schema, and ADR; the decision repository moved to Task 2 rather than creating a nonfunctional stub. This avoided an unusable intermediate module, at the cost of a sequential dependency between tasks.
3. **Operational decision retention.** Decision records remain immutable while their campaign and source turn exist, but scoped deletion cascades on explicit campaign deletion or source-turn removal. This preserves existing deletion and rewind behavior; the decision audit cannot outlive its deleted source or campaign.
4. **Identity in detail fingerprints.** Include the owning proposal identity as well as source and observation in a detail decision's fingerprint. Identical quotes or values for two people must not suppress each other. This required a helper and test refinement and makes matching identity-sensitive; no deployed data needed migration at the time.
5. **Split Task 2.** Separate decision storage and read integration (2a) from write-path publication and attach fences (2b) to keep implementation and review manageable. The cost was another review gate and a sequential dependency; both parts remained required before exposing the feature.
6. **Preserve the existing write fence in 2a.** Move the existing `resolveDetail` duplicate-dismiss guard into 2a when its shared SQL was changed, so the already-active API could not regress between split tasks. This slightly expanded 2a; new publication and delegation remained in 2b.
7. **Legacy dismissals.** Keep earlier detail-dismissal suppression without silently migrating old records. The new Dismissed and Undo view covers journal decisions made by this workflow, with that limitation explained in the UI and guide. The cost is that earlier dismissals cannot be listed or undone there.
8. **Split Task 3.** Deliver API and contracts (3a) before the shared UI and browser work (3b), because of task size. This added a gate and sequencing overhead; both parts remained in scope.
9. **Split Task 5.** Separate pure contracts and projection (5a) from transaction and publication work (5b), after the Stage A gate. This made the work reviewable at the cost of an extra gate; it did not drop requirements.
10. **Identity continuity after creation.** Derive continuity from scoped persisted resolution and provenance when a previously unresolved proposal is later rescanned with a character ID. Globally ignoring identity would suppress distinct people. This required shared matching changes and regression tests; ambiguous bindings must remain conservative.
11. **Field policy for retractions.** Preserve the accepted seeded-appearance policy of latest valid observation, while retaining conflict handling for non-seeded static fields. Profile and context must agree within the applicable policy, rather than forcing identical policy across fields. The cost was explicit policy coverage and specification clarification; captured-context proof remained required in 5b.
12. **Split Task 5b.** Build the transaction writer with the minimum standard read projection (5b1), then capture, provenance, and duplicate-publication handling (5b2). A standalone writer without an effective read projection was not sufficient. The split added a gate but retained the original scope.
13. **Split Task 5b2.** Deliver capture and provenance (5b2a), followed by duplicate-publication suppression (5b2b), sequentially. Version 1 captures needed frozen retraction metadata, while absent metadata had to preserve historical fingerprints. The added gate increased coordination but kept both requirements explicit.
14. **Split Task 7.** Deliver typed API and status (7a) before the shared UI and browser work (7b), only after compatible readers passed Task 6. This provided an explicit UI contract and added a gate without reducing scope.
15. **Task 6 implementation seams.** Treat its file list as expected seams rather than requiring cosmetic edits to existing replay or merge code when behavior is demonstrated. Place merge regressions in the observation-decisions suite where appropriate. This preserves established shared logic; if the evidence exposes missing behavior, it must be fixed rather than hidden by a no-op edit. Linux-only secure-staging skips remain unverified, not passing Linux evidence.
16. **Split Task 8.** Separate the composed proof (8a) from broader browser, documentation, and performance work (8b), while the root ran host unit and PostgreSQL checks. This added a review gate and coordination but retained all original checks.

The subsequent whole-branch review of `8eeecef3..bbe5d100` required batching Dismissed reads, inline stale-fact recovery, and stronger network-error correlation. Fix commit `41e12479` addressed all three; its scoped independent review found no new Critical or Important issue. Scoped active decisions and identity bindings still materialize in memory, so large histories remain a scaling consideration. Linux staging and release checks, physical mobile keyboard behavior, live-provider behavior, and production activation were not verified.
